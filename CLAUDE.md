# K6UI — Project Guide

A web UI for building and running [k6](https://k6.io) load tests without writing code.
Stack: Express (ESM) + vanilla JS frontend. **No build step, no framework.** Tests use Node's
built-in runner (`npm test`); browser checks live in `scripts/` (see Verification).

## Running

```bash
npm start        # http://localhost:3000
npm run dev      # auto-restart on server file changes
```

Prerequisites: Node 18+, and the `k6` binary on PATH (only needed to run tests; script generation works without it).

## Data flow

UI form → `collectConfig()` (js/config.js) → `POST /api/generate` or `/api/run`
→ `generateScript()` (server/generator) → [run only] `k6-runner.js` spawns k6
→ SSE events → `js/runner.js` renders the live log, request detail table, and metrics.

## API

| Endpoint | Body | Response |
|---|---|---|
| `GET /api/k6-status` | — | `{ installed, version? }` |
| `POST /api/generate` | config object (≤ 24 MB, to carry data files) | `{ script }`, 400 `{ error }`, or 413 `{ error }` (data file or body too big) |
| `POST /api/import-script` | `{ script }` (k6 source) | `{ config, warnings: [{ line, message }] }` or 400 `{ error, warnings }` |
| `POST /api/import-jmx` | raw .jmx XML (`Content-Type: application/xml`, ≤ 10 MB) | same as `/api/import-script` |
| `POST /api/run` | config object (≤ 24 MB) | SSE stream (events below), or the same 400 / 413 JSON before it starts |

SSE events from `/api/run`: `status` (progress), `log` (raw k6 output line), `req-log`
(one request record, see "Request details" below; at most 50 passed + 50 failed a second),
`req-log-skipped` (`{ skipped }`: running total of records left out by that limit and by the script's per-VU budget, a lower bound), `export` ("Save to CSV" rows: `{ file, columns, rows, truncated }`,
batched, all sent before `done`), `metrics` (live, about once a second while k6 runs, never after `done`, see "Live metrics" below), `error`, `done` (`{ code, summary }` — summary
from `k6 --summary-export`; plus `outcomes` when a request has outcome rules, `outcomeThresholds` when outcome targets are set, and `race` in race burst mode, see below; the runner's own `raceRecords` never reaches the browser). Exit code 0 = all thresholds met; 99 = thresholds failed.

`metrics` event (`server/live-metrics.js` `readLiveMetrics()`; every value covers the whole run so far, `null` until k6 reports it):

```jsonc
{
  "vus": 4,                 // VUs running now (k6 `vus`)
  "requests": 1234,         // `http_reqs` count
  "requestRate": 410.2,     // `http_reqs` per second since the start
  "durationAvg": 12.3,      // `http_req_duration` average, ms (cumulative, not per second)
  "durationP95": 40.1,      // `http_req_duration` p(95), ms (cumulative)
  "failedRate": 0.01,       // `http_req_failed` rate, 0 to 1
  "outcomeCounts": { "k6ui_outcome{rq:1,outcome:success}": 12 },  // every outcome submetric
  "outcomes": [ /* as in done, from outcomeCounts; only with outcome rules */ ],
  "outcomeThresholds": [ /* as in done, live status (below); only with outcome targets */ ]
}
```

## Configuration object schema

The same object is used for `/api/generate`, `/api/run`, and project save files.

```jsonc
{
  "scenario": {
    "groups": [{                       // optional (default []): one level, requests join through their groupId
      "id": "grp_order", "name": "Order flow", "enabled": true, "collapsed": false,
      "headers": [{ "key": "X-Service", "value": "orders" }],
      "runIf": {                       // optional; absent or null = always runs
        "variable": "EXECUTION_MODE",  // [A-Za-z_]\w*, read like {{EXECUTION_MODE}} when the group starts
        "operator": "one-of",          // "equals" | "not-equals" (one value) | "one-of" (one or more)
        "values": ["ORDER_FLOW", "ALL"]  // compared as strings, case-sensitive
      }
    }],
    "requests": [ /* request, see below; "groupId": "grp_order" puts it in a group */ ]
  },
  "variables": [{ "key": "base_url", "value": "https://api.example.com" }],
  // global variables, usable as {{base_url}} in any url/header/body;
  // keys must be valid JS identifiers ([A-Za-z_]\w*) — others are ignored
  "dataSets": [{                       // CSV data files, optional (default []): one row per iteration
    "id": "ds_login", "name": "Users", "fileName": "login.csv",
    "delimiter": ",",                  // one character; "\t" = tab
    "skipHeader": true,                // the first row is a header, not data
    "columns": ["email", "password"],  // column i of the file → {{email}}; [A-Za-z_]\w* only, blank skips a column;
                                       // empty list + skipHeader = names from the header
    "content": "email,password\nuser1@example.com,pass1\n",  // the CSV text itself (≤ 5 MB per file, 10 MB total)
    "share": "next-row",               // "next-row" (default): exec.scenario.iterationInTest, shared by all VUs; "per-vu": __VU - 1
    "onEnd": "recycle",                // "recycle" (default): wrap around; "stop": end the iteration early, one log line
    "groupId": "grp_order"             // optional: read the row, and apply "stop", only when this group starts (absent or "" = every iteration)
  }],
  "globalHeaders": [{ "key": "Accept", "value": "application/json" }],
  // headers merged into every request; a request-level
  // header with the same name (case-insensitive) overrides the global one
  "load": { "mode": "simple", "vus": "10", "duration": "30s" },
  // or: { "mode": "stages", "stages": [{ "duration": "30s", "target": "20" }] }
  // or: { "mode": "iterations", "vus": "5", "iterations": "2", "maxDuration": "1h" }
  //     every VU starts at once and runs the flow `iterations` times, then stops
  //     (k6 `per-vu-iterations` scenario); maxDuration is optional, default "1h"
  // or: { "mode": "race", "vus": "4", "maxDuration": "1h", "race": {   // race burst, see below
  //       "request": "req_redeem",        // request id; "" = the first request that runs
  //       "timing": "offsets",            // "together" | "spread" | "offsets"
  //       "spreadMs": "200",              // spread: VU i (from 0) at round(i × spread / (VUs − 1)) ms
  //       "offsets": "0,{{T2_MS}},{{T2_MS}},1030",  // offsets: one per VU (ms); VUs = how many
  //       "leadMs": "2000",               // T0 = the end of setup() + lead
  //       "warmup": true, "warmupPath": "/",  // GET <origin of the race request><path> before the wait
  //       "failIfLate": false }           // a late VU fails the run
  //     numbers: a number ≥ 0 (VUs: whole, ≥ 1) or {{global variable}}, resolved when generated
  "thresholds": { "p95": "500", "errorRate": "1",     // empty string = unused
    "outcomes": [                                      // optional outcome targets (Thresholds / SLA → Outcome Targets)
      { "request": "req_redeem", "label": "success", "op": "<=", "value": "{{QUOTA}}" }
      // request = a request id; label = one of its outcome labels (fallback included);
      // op "<" | "<=" | "==" | ">=" | ">"; value = a number ≥ 0 or {{global variable}}
    ] },
  "options": {                                         // request details (Run & Results → Requests)
    "logRequests": true,                               // enables req-log events (off by default)
    "logFilter": "all",                                // "all" | "errors" (failed only) | "sample"
    "logSampleEvery": 10,                              // "sample": every Nth iteration of each VU (__ITER % N === 0) plus every failure; 1–10000
    "logRedact": false                                 // "Hide secrets": [REDACTED] for secret headers/fields (off by default = values as sent)
  }
}
```

Shape of one request:

```jsonc
{
  "type": "http",                // "http" (default) or "grpc"
  "method": "GET",
  "url": "https://api.example.com/{{id}}",
  // gRPC requests: url = "host:port", body = request message JSON,
  // headers = metadata, plus:
  "grpcMethod": "",              // "package.Service/Method"
  "grpcPlaintext": false,        // true = connect without TLS
  "headers": [{ "key": "Authorization", "value": "Bearer {{token}}" }],
  "body": "",                    // only used for POST/PUT/PATCH/DELETE
  "checkStatus": true,           // add the automatic status check (200–399, or the expected statuses)
  "expectedStatuses": "200,400", // optional, HTTP only: statuses that count as a success (codes, classes like 4xx;
                                 // absent or "" = k6's own rule, 200–399), see "Expected statuses" below
  "sleepAfter": "1",             // seconds to pause after the request
```

- The Build Flow view shows which `{{variables}}` exist and warns on a request card when it sends one it cannot use yet (`public/js/variables.js`, which repeats the generator's rules below; keep the two in step: `test/variables.test.js` compares them on generated scripts).
- `{{varName}}` interpolation in url/headers/body uses global variables, data file columns, values extracted by earlier requests, and `vars.<name>` assignments made by earlier pre/post-processor scripts (precedence: extracted > processor > data column > global); unknown names are left as literal text. A column and an extraction with the same name therefore read the file until the extracting request has run, and the extracted value after it.
- `{{$name}}` is K6UI's own namespace (dynamic variables; user variables, columns and extractions are `[A-Za-z_]\w*` and can never take one), resolved only through `ctx.dynamicVars` in `server/generator/interpolate.js`; an unknown `$` name stays literal text. Today there is one: `{{$outcome}}`, the label of the latest request with outcome rules in this iteration, in Save to CSV columns (of that request and later ones) and in the URL, headers and body of later requests. It is known from the first request with rules on (in generate order, like an extraction): before that it stays literal text, and in that request's own URL it is still the previous label. When a request that runs uses it, the default function starts with `let $outcome = "";` and each labelled request adds `$outcome = outcome_main_<i>;`, so a skipped conditional group leaves the previous label (or `""`). Not available in processor scripts. The k6 importer reads `${$outcome}` back as `{{$outcome}}` and skips K6UI's own declaration and assignments, when the script declares K6UI's outcome helpers; elsewhere `$outcome` is an ordinary name.
- Data files (`dataSets`, `server/generator/data.js`) embed the rows in the script as `new SharedArray(...)` built from a JSON literal (imports `k6/data` and `k6/execution` only when a data set is used), so View Script and a standalone run need no extra file and `k6-runner.js` is untouched. At the start of the default function each data set picks its row `DATA_n_ROW` (`next-row`: `exec.scenario.iterationInTest`; `per-vu`: `__VU - 1`; `recycle` = modulo; `stop` = `return` after a `sleep(1)` so duration tests do not spin, with one `console.warn`: once for the whole test with `next-row`, once per VU with `per-vu`). A global data set (no `groupId`) reads its row for every iteration, whether or not the requests that use it run; a data set tied to a group is read only when that group starts (see the conditional groups bullet). A data set with no content, no rows, or no valid column is ignored (its `{{placeholders}}` stay literal text); the first data set that has a column name wins. A file over 5 MB (or 10 MB in total) is a 413, an unclosed quote a 400. `express.json` takes 24 MB on `/api/generate` and `/api/run` only; the import endpoints keep 1 MB. The CSV reader (`public/js/csv-parse.js`: quotes, delimiter, CRLF, BOM, empty lines) is shared with the UI so the preview and the script always count the same rows. Needs k6 with `k6/execution` (v0.38+). The data is saved in the project file and written into the script, so a file with credentials makes both sensitive.
- `iterationInTest` is unique per iteration across all VUs of the scenario, also for the `per-vu-iterations` scenario of iterations mode (checked with k6 v2.4.0 in `test/data-files-k6.test.js`, which skips when `k6` is missing): 5 VUs x 1 iteration over 5 rows reads 5 different rows.
- Conditional groups (`runIf`, `server/generator/run-if.js` + `public/js/run-if.js`): a group's requests are wrapped in `if (...) { ... }` in the default function. The condition is data, never free JavaScript. The variable is read by the same precedence as `{{variable}}` (extracted > processor > data column > global) **when the group starts**, and values are compared as strings (`String(x) === "A"`, `!==`, or `["A","B"].includes(String(x))`; case-sensitive). The condition is checked once per *run* of the group: requests of one group that are not next to each other (Auth, Checkout, Auth) are separate runs, each with its own `if`. A variable that is not known when the group starts (not global, not a column of a file outside this group, not extracted or assigned by an earlier request) is a **400** naming the group and the variable, as is a condition that cannot work (bad name, operator or values); the UI blocks Run / View Script for a half-typed row. The block is not re-indented (a request body can hold raw newlines inside a template literal), so the generated `if` looks flat. Everything of a request stays inside it: processors, assertions, request log, `sleep`, gRPC.
  - Variables hoisted out of the block: names extracted by the group's requests that are not declared yet get `let name = "";` above the `if` — or `let name = "<default>";` when an extraction of that name in the run has a default (the first one, in request order) — so a request after the group can still use `{{name}}`; inside, they are assigned, never re-declared. The *precedence* rule is unchanged (a name counts as extracted only after the request that extracts it, in generate order). When the group does not run the value stays at that default, else `""`; a name already extracted before the group is not hoisted again and keeps its earlier value. Names a processor script assigns to `vars` inside the group start as `""` outside it.
  - Data files of a group (`groupId`): the row variable is declared up front (`let DATA_n_ROW = { column: "", ... }`), and the row is chosen, and `stop` applied (an early `return`), at the start of the group's run, inside the `if` when there is one. A data file of a **turned-off** group is not used at all (no SharedArray, no size-limit count, its `{{columns}}` stay literal text); a `groupId` that points nowhere means global. The row is picked by `exec.scenario.iterationInTest` (or `__VU - 1`), so the row index follows the iteration number, **not** how many times the group ran: if the condition holds in only some iterations, rows are skipped.
  - Importing: JMeter `IfController` directly under the thread group → a group with `runIf` (see the JMeter bullet); K6UI's own generated `if` is read back by `importer/run-if.js` (the group name comes from the `// Group "…" runs only if` comment above it); any other `if` in a k6 script is skipped with a warning that its requests were left out.
- JSON extraction from an HTTP response is `res.json("<gjson path>")` (k6 reads the path in Go), never `JSON.parse(res.body)` in JavaScript: on a three-request flow that parse halved the requests per CPU second, which made K6UI slower than JMeter (numbers in `docs/baseline-performance.md`). `buildGjsonPath()` (`server/generator/helpers.js`) turns the selector into the path: `items[0].id` → `items.0.id`, `[0].id` → `0.id`, `grid[1][2]` → `grid.1.2`, empty parts dropped, and every key character gjson reads as syntax (anything but letters, digits, `_ - :`, spaces and non-ASCII) escaped with `\`, so `*`, `#`, `@`, `$` … stay literal keys as before (checked with real k6 in `test/extraction-defaults-k6.test.js`). An empty selector is `res.json()` (whole body; throws for a body that is not JSON). gRPC still reads the decoded `res.message` with a JS accessor. The k6 importer reads `res.json(path)` back through `splitSelector()` (`server/importer/flow.js`: `\` escapes undone, number → `[n]`). The Node test stub (`test/helpers/load-script.js`) implements the same `res.json(path)` subset.
- Extraction defaults (`default`, `server/generator/extract.js`): fixed text only, never an expression. Without one (absent or `""`): a regex with no match gives `""`; a missing JSON path or header gives `undefined`, and so does a JSON path on an empty body or a body that is not JSON (the iteration carries on; before JSON was read with `res.json()` such a body threw and k6 ended the iteration). With one, the read is wrapped in `extractOr(() => <read>, "<default>")`, a helper written once above the default function only when an extraction that runs has a default: the default is used when the read gives `undefined` or `null` or throws (missing path or header, no regex match, a body that is not JSON, no body). A match that is `""`, `0` or `false` is kept. The same default is the value a skipped conditional group leaves behind (see above). A number or boolean default in a project or API payload is read as text; strings are kept as typed (not trimmed), including in the UI, where an empty input means no default. Importing: JMeter's "Default Value" of JSON (`defaultValues`, one per variable, `;`-separated), Regex and Boundary extractors becomes `default`; an empty one, or one with `${...}` (a warning), gives none. In a k6 script, `x || "text"` and `x ?? "text"` (string, number or plain template literal) on a value read from a response become the default (`|| ""` stays "no default"; with nested fallbacks the inner one wins, as in JavaScript), as does K6UI's own `extractOr(...)` when the script declares the `extractOr` helper. JSR223 / BeanShell post-processors (custom fallback logic) are never imported: the warning names the variables they `vars.put`.
- Save to CSV (`exports`, `server/generator/csv-export.js` + `public/js/csv-export.js`): k6 cannot write files, so after the request the script logs one row: `console.log(JSON.stringify({ k6uiExport: "<file>", columns: [...], row: [...] }))`, the values interpolated like a URL. `k6-runner.js` hands every console line that starts with `{"k6uiExport":` to `server/export-collector.js` and never to the live log (a broken one is dropped too, since it may hold a token). The collector keeps the rows in memory only, at most 5 MB of CSV per file, 10 MB in total and 10 files (later rows are dropped and the file is marked `truncated`), and sends them as `export` events every 250 ms and before `done`, so a stopped run keeps what reached the browser. The browser (`public/js/export-results.js`) keeps them in the tab until the next run, offers Download CSV (a Blob, nothing goes back to the server) and Use as data file (`useAsDataFile()`: fills the data file with that file name, for example the empty one a .jmx import created, after a confirm when it already has other rows, or adds one; header row on). `skipMissing` wraps the line in `if (![undefined, null, "", <every default of that extraction>].includes(name) && ...)` over the extracted variables the columns use; with none it has no effect and imports back as `false`. Column names are `[A-Za-z_]\w*` (they become `{{columns}}` of a data file), unique; two requests saving to one file must use the same columns; an export that breaks a rule is a 400 naming the request (and the UI reports it before Run). Turned-off requests and groups save nothing, a skipped conditional group saves no row. The k6 importer reads K6UI's own line (and its `if`) back into `exports`; the JMeter importer never translates a JSR223 post-processor that writes a file (Groovy), its warning points to Save to CSV.
- Before/After sub-requests (`pre` / `post` on a request) no longer exist in the editor: ordering requests does the same job. `expandSubRequests()` (`public/js/sub-requests.js`) reads them from an older project (in the store, on open) or an API payload (in the generator) as ordinary requests in the same order: `<name> (before)`, the request, `<name> (after)`, with ids `<id>_before` / `<id>_after`, the same group and on/off state, the automatic status check on and no pause. The request's own pause and "Save to CSV" rows came after its After request, so they move to it. Saving writes no `pre` / `post` keys.
- Request details (`options.logRequests`, `server/generator/index.js` + `public/js/request-log.js`): with recording on, the script gets a `REQUEST_LOG` constant (`{ filter, every, redact, bodyLimit }`) and helper functions; after each request `try { logHttpRequest(i, method, url, res); } catch (e) {}` (gRPC: `logGrpcRequest(i, address, method, message, metadata, res, durationMs)`) prints one `{__r:1,...}` JSON line: `vu`, `it`, `i`, `m`, `url`, `s` (status), `d` (ms), `ok` (200–399, or the request's expected statuses; gRPC status 0), `oc` (the outcome label, only for a request with outcome rules), `er` (k6's `res.error`), `rqh` / `rq` (request headers and body, from k6's `res.request`), `rh` / `rb` (response headers and body). Redaction is off by default (records show every value as sent and received); with "Hide secrets" (`logRedact: true`) it runs inside k6, before anything leaves the script: Bearer tokens, secret-looking JSON/form fields (`"password":"[REDACTED]"`, quotes kept so JSON stays JSON), secret query parameters, and the whole value of any header whose name holds authorization, cookie, token, secret, password, api key, session, signature or credential. Bodies are cut at 4,096 characters with a `… [N more characters not shown]` note, header values at 1,024. `k6-runner.js` hands these lines to `request-log-throttle.js` (never to the live log); the browser keeps the 500 most recent and shows each as Request / Response with headers and an indented JSON body. A request with outcome rules or expected statuses calls `logHttpOutcome(i, method, url, res, oc, ok)` instead (`oc` = `outcome_main_<i>` or `undefined`; `ok` = the expected-status test, else 200–399); `logHttpRequest()` keeps its four arguments, because a six-parameter version called with four cost about 10% of the requests per CPU second with "all" (k6's interpreter). The table has an Outcome column (empty for a request without rules) and the report keeps `outcome` per record. The Request side of an HTTP record has "Copy as cURL" (`public/js/curl-export.js` `curlFromRecord()`): `curl '<url>'` with `-X` only when curl would not infer the method (`--head` for HEAD), `-g` for a URL with `[ ] { }`, one `-H` per recorded request header except `Content-Length`, and `--data-raw` with the recorded body, every value in single quotes; `notes` (shown under the button) say when the command cannot match the request: a body or header value cut at the size cap (the cut note is removed, the recorded part is sent), `[REDACTED]` values copied as they are, no recorded headers. gRPC records have none. The report shows the same command under each HTTP record, as text (it runs no scripts). Every column heading of the table is a sort button (ascending, descending, then arrival order; `public/js/request-sort.js`): records that arrive later are inserted where the sort puts them, an open detail row moves with its row, the sort stays for later runs in the tab (memory only, never saved). Logging every request costs k6 time under load, so "errors" and "sample" exist; the filter is checked before anything is built. After the filter, each VU keeps a record budget (`takeLogBudget()`, a token bucket per VU, passed and failed apart): `REQUEST_LOG.burst` records at first, then `REQUEST_LOG.rate` a second, from `requestLogBudget(options)` in `server/generator/index.js`: `rate` = 2 × 50 / the most VUs the load profile runs at once (all VUs together write about twice what the server forwards, so the server limit still decides what is shown), `burst` = 500 / those VUs, 1 to 10 (a short race run, every VU sending one burst of requests, still records them all). A VU over its budget builds nothing and counts the record; its next record carries the count as `sk`, which `request-log-throttle.js` adds to the skipped total and removes. What a VU leaves out after its last record is never counted, so the UI says "At least N". Without the budget, logging "all" cut a 50-VU run from ~48k to ~17k requests a second while the server dropped 99.5% of the records. The k6 importer reads `REQUEST_LOG` back into `logFilter` / `logSampleEvery` / `logRedact` (a K6UI script without `redact` predates the option and always redacted, so it imports with `logRedact: true`).
- Pre/post-processor scripts are inlined as `{ ... }` blocks (post gets the response as `const res`) and share a per-iteration `vars` object. Referencing `crypto.` or `encoding.` in a script auto-adds the `k6/crypto` / `k6/encoding` import. Execution order per request: pre-processor → request (+ check/extract) → assertions → post-processor. Scripts are syntax-checked at generate time (`new Function`) — invalid code returns a 400 with the request number.
- gRPC requests (`type: "grpc"`) generate `k6/net/grpc` unary calls with server reflection (`reflect: true` — the target server must support it; .proto upload is not implemented). The automatic check compares against `grpc.StatusOK`; extractions read the decoded `res.message`; assertions are remapped for gRPC (statuses = gRPC codes, body = `JSON.stringify(message)`, `duration-lt` is skipped). Pre/post sub-requests stay HTTP.
- Outcome rules (`outcomes`, `server/generator/outcomes.js` + `public/js/outcomes.js`, editor part "Label each response"): data, never JavaScript. Every response of an HTTP request with rules gets one label, the first rule (top to bottom) whose status matches and, for a source other than `none`, whose value matches; a response no rule matches gets the fallback. `json` reads `res.json("<gjson path>")` once per path per response (a missing path, a body that is not JSON: no value; an empty path is the whole body; an object or array is compared as JSON text), `header` matches the name exactly first, then case-insensitively, `body` is the response text. Values are compared as text, exactly (`equals`), as a substring (`contains`) or with a regex (`matches`; `/source/flags` with i, m, s, u; g and y are dropped); `exists` is "not undefined or null" and is refused for the body. The script gets `import { Counter } from 'k6/metrics'`, `const OUTCOME = new Counter("k6ui_outcome")` and small helpers (`outcomeJson`, `outcomeHeader`, `outcomeText`, `outcomeContains`, `outcomeMatches`; written once, only when a request that runs has rules), and per request at the top level: `const OUTCOME_RULES_<n> = { rules: [...], fallback }` (the rules as data, a JSON path stored as its gjson path; only the importer reads it), `OUTCOME_TAGS_<n>` (one tag object per label, built once), `OUTCOME_PATTERNS_<n>` (the regexes, compiled once per VU) and `function outcomeOf_<n>(res)`, one `if (...) return "<label>"; // rule <k>` per rule, then `return "<fallback>"`; a JSON path is read at most once per response (`json_<k>`, on first use). After the request's extractions: `const outcome_main_<i> = outcomeOf_<n>(res_main_<i>);` and `OUTCOME.add(1, OUTCOME_TAGS_<n>[outcome_main_<i>]);`, which adds 1 to `k6ui_outcome{rq:<n>,outcome:<label>}`. A function per request instead of one helper looping over rule objects: k6's interpreter made that loop cost about twice as much per response (numbers in `docs/baseline-performance.md`). `<n>` is the request number of the run (enabled requests in runnable groups, from 1, as in error messages and the Requests table). k6 reports a submetric in `--summary-export` (and its REST API) only when it has a threshold, so every label gets `count>=0`, which always passes and is hidden from the report's targets; a label with no responses still reports 0, also when the request never ran. `generateScript(config, meta)` fills `meta.outcomes` (`[{ rq, index, name, method, url, labels, fallback }]`) and `/api/run` adds `outcomes` (`readOutcomeResults()`: `[{ rq, name, method, url, fallback, total, outcomes: [{ label, count, share }] }]`) to `done`, shown under Outcomes in the Overview and in the report. Rules that cannot work (no or bad label, bad status, header without a name, `exists` on the body, a bad regex, more than 10 labels with the fallback, rules on a gRPC request) are a 400 naming the request, and the UI reports them before Run; empty rule rows are ignored. The k6 importer reads K6UI's own `outcomeOf_<n>(res)` line back from `OUTCOME_RULES_<n>` (only when the script declares the one-argument `outcomeText` helper), skips the `OUTCOME.add(...)` line, the `count>=0` thresholds and the `k6/metrics` import without a warning, and never reads the `if`s of the function. Outcome rules label a response; they do not decide whether it failed: that is the request's expected statuses (below).
- Expected statuses (`expectedStatuses`, `server/generator/expected-statuses.js` + `public/js/expected-statuses.js`, editor part "Success statuses"): the statuses that count as a success for one HTTP request, for example `"200,400"` in a race test where a 400 "quota reached" is the right answer. Codes and classes (`4xx`) separated by commas, the same syntax as an outcome rule's status; empty or absent = k6's own rule (200–399). The script gets one top-level `const EXPECTED_STATUSES_<n> = http.expectedStatuses(200, { min: 400, max: 499 });` per request with a list (built once per VU at init; `<n>` = the request number of the run) and `responseCallback: EXPECTED_STATUSES_<n>` in that request's params, so k6 counts only the other statuses in `http_req_failed` (and tags them `expected_response:false`). The automatic status check becomes `"status 200,4xx: request <n>": (r) => r.status === 200 || (r.status >= 400 && r.status < 500)`, and `ok` of the request record uses the same test, so an expected rejection is a passed record (not under the "errors" filter, not an entry under Errors). A request without a list generates exactly as before. A list that does not parse, or one on a gRPC request, is a 400 naming the request (the UI reports it before Run). "Use statuses from outcome rules" fills the field with the statuses the request's rules name, in rule order, leaving out 5xx (a server error stays a failure unless typed in) and rules for any status. The store keeps the normalized text (`"200, 4XX"` → `"200,4xx"`; an unparsable list is kept as typed so Run names it; `""` or a value that is not text or a number drops the key). The Simple notice counts requests with a list; the report's request table gets a "Success statuses" column when one has a list. The k6 importer reads `responseCallback: http.expectedStatuses(...)` (inline or a top-level constant; codes, `{ min: X00, max: X99 }` → `Xxx`, a range under 10 codes → its codes; anything else is a warning) and, for a request with a list, a check that tests exactly that list as its status check (`checkStatus: true`). `http.setResponseCallback()` is not read (top-level code warning).
- Outcome targets (`thresholds.outcomes`, `public/js/outcome-thresholds.js`, Thresholds / SLA → Outcome Targets): pass criteria on how many responses of one request got one outcome label, such as `success <= {{QUOTA}}` in a race test. `planOutcomeThresholds(config)` numbers the requests like the generator (enabled, in a group that is on, with a URL, from 1) and checks every target; the UI runs the same function before Run. Each target becomes one more expression on its label's submetric, after the always-passing one: `"k6ui_outcome{rq:2,outcome:success}": ["count>=0", "count<=300"]` (an expression already in the list, such as a target `>= 0`, is not repeated: k6 keys results by expression). k6 reads `options` at init, so `value` is a number (≥ 0, decimals allowed) or `{{name}}` of a global variable whose value is such a number, resolved when the script is generated. A **400** naming the target (`Outcome target <n>: ...`, n = its position in the list) for: no request chosen, a request id that is not in the project, a request without outcome rules, a label that request does not have, a comparison that is not one of the five, an empty or non-number value, and a `{{name}}` that is a column of a data file the run reads, is extracted by a request that runs, is set by a script (`vars.name`), is not a global variable, or is a global whose value is not a number.
  - A target whose request does **not run** (turned off, in a turned-off group, no URL) is **not checked**: it is left out of the thresholds and not validated beyond its request existing, the script names it in a comment, and Run & Results lists it as "Not checked" with the reason. Deliberate: turning a request off for a quick run does not need its targets removed first, and the results still show the target was not checked.
  - The generator also writes `const OUTCOME_THRESHOLDS = [{ rq, label, op, value }]` (as typed) after `options`, for the importer only. `meta.outcomeThresholds` (the plan) lets `/api/run` add `outcomeThresholds` to `done` (`readOutcomeThresholdResults()`: each target with `status` `met` / `not-met` / `skipped` / `unknown` (no summary) and the label's `count`; in a k6 summary export a threshold value `false` means it passed). The Overview lists them above the per-request outcomes, a target not met is also an entry under Errors, and the report's Targets table shows them as typed (`count <= {{QUOTA}} (300)`, `Met (counted 2)`).
  - The store keeps one shape (`{ request, label, op, value }`, text trimmed, blank rows dropped; absent stays absent) and follows a request id it had to change (case, spaces, a repeat). The k6 importer reads `count<op><n>` on `k6ui_outcome{rq:<n>,outcome:<label>}` back as targets on the request whose `outcomeOf_<n>()` line it read (a request it could not map, or a label its rules do not have, is a warning); order and a `{{variable}}` come back from `OUTCOME_THRESHOLDS` when that variable still stands for the same number, else the number is imported; `count>=0` is a target only when that list has it.
- Race burst (`load.mode: "race"`, `public/js/race.js` + `server/generator/race.js`, Load Profile → Race burst): every VU runs the flow once (k6 `per-vu-iterations`, `iterations: 1`) and sends one request of it, the **race request**, at a planned time T0 + its offset. `setup()` returns `{ k6uiRaceT0: Date.now() + RACE.leadMs }`, so T0 is one clock for all VUs and does not move with how long `setup()` took (the old preScript barrier anchored on `exec.instance.currentTestRunDuration`, which includes it); the default function becomes `export default function(data)`. Requests before the race request run first (log in, create an order) and must fit in the lead time. Right before the race request's **pre-processor** (so a timestamp or signature it computes is fresh), the script calls `k6uiRaceWarmup(<the race URL>)` (with the warm-up) and `const race_at_<i> = k6uiRaceWait(data.k6uiRaceT0);`, which sleeps until T0 + offset − `RACE.spinMs` and busy-waits the rest on `Date.now()` (k6 has no `performance.now()`, so 1 ms resolution), then returns the planned time. `spinMs` is 3 up to 500 VUs and 0 above (busy-waiting VUs fight over the cores: one 1000-VU probe run spread 34 ms). A VU that gets to the wait at or after its time is **late**: it adds 1 to the Counter `k6ui_race_late` and sends at once. That metric always has `count>=0` (so the summary reports it, 0 included) and, with `failIfLate`, `count==0` (the run fails, exit 99); without it a late VU is a warning. See "Race burst results" below for what `done` carries. The **warm-up** is one `GET <origin of the race URL as sent><warmupPath>` per VU before the wait, tagged `k6ui: "warmup"`, with every status expected (`RACE_WARMUP = http.expectedStatuses({ min: 100, max: 599 })`, so not in `http_req_failed`), but it still counts in `http_reqs` and the response times (the UI says so). k6 reuses connections per host, so the race request goes out on the warm-up's connection: with 200 VUs, 0 race requests on a new connection, against 50 of 50 with no warm-up and no earlier request (`test/race-k6.test.js`). A URL that reads a `{{name}}` its own pre-processor sets has no origin before that script runs: a 400 while the warm-up is on. Timings: `together` (every offset 0), `spread` (evenly from 0 to `spreadMs`, whole ms) and `offsets` (one per VU, and the VU count is how many there are; the UI shows it read-only). Every number is a number or a `{{global}}` holding one, resolved when the script is generated (same rules as outcome targets: a data column, an extracted value or a `vars.x` is a 400). The plan (`const RACE = { request, offsets, leadMs, spinMs, warmupPath, config }`, `config` = the form as typed) is written once at the top. A **400** naming the field (`Race burst: ...`) for: a race request that is gone, does not run or is gRPC; no request that runs; an unknown timing; no offsets, an offset or spread or lead that is not a number ≥ 0 (or not a usable global); VUs not a whole number ≥ 1; a warm-up path that does not start with `/` or has spaces. The UI runs the same `planRace()` before Run. The store keeps one shape for `load.race` (every key, numbers as text, offsets as trimmed comma-separated entries, an unknown timing kept so Run names it) whenever the mode is race or the project has one, and follows a request id it had to change. A script without race mode is byte-identical to before (`test/race-off-characterization.test.js`). The k6 importer reads K6UI's own race back (when the script declares `k6uiRaceWait(t0)`): the per-vu-iterations scenario + `RACE.config` → race mode, the request after `k6uiRaceWait()` → `race.request`, the warm-up call, `setup()` and the `k6ui_race_late` thresholds without warnings. The Load chart shows the planned send time of each VU (dots after T0), the Simple notice lists "Race burst (Load step)". Send times are k6's (`Date.now()` before the request), not arrival times at the server.
  - Race burst results (`server/race-collector.js`, `readRaceResult()` in `public/js/race.js`, `public/js/race-results.js`, `public/js/race-gantt.js`): `k6uiRaceWait()` keeps when the VU reached it (`k6uiRaceArrived`, the same `Date.now()` its late test uses); the race request gets `const race_sent_<i> = Date.now();` right before `http.request` (after the pre-processor and the body) and, after its extractions and outcome label (before the request-record line), `try { k6uiRaceRecord(data.k6uiRaceT0, race_at_<i>, race_sent_<i>, res_main_<i>, <outcome_main_<i> or undefined>); } catch (e) {}`, which logs one `{"k6uiRace":1,"vu","t0","at","ar","sent","ms","cn","s","ec"?,"oc"?}` line: T0, planned time, arrival at the wait, send time (epoch ms), how long the request took (`blocked + connecting + tls_handshaking + duration` of `res.timings`, sub-ms), whether it connected (`cn`: connecting or TLS > 0), status, k6's `error_code` (when not 0) and the outcome label. These lines are logged in every race run (one per VU, regardless of request details) and go to `race-collector.js`, never to the live log; the collector checks each field, keeps at most 10,000 and hands `{ records, dropped }` to `done` as `raceRecords`, which `/api/run` turns into `race`. `readRaceResult(plan, summary, raceRecords, { labels, fallback })` → `{ rq, name, method, url, vus, failIfLate, late, timing, leadMs, labels, fallback, t0, sent, missing, dropped, records, stats }`: `late` is k6's count when there is a summary, else counted from the records (arrived ≥ planned); `records` are per VU, times in ms after T0, by planned time then VU: `{ vu, offset, arrived, sent, ms, late, status, errorCode, outcome, newConnection }`; `sent` = records, `missing` = VUs that never sent the race request (their iteration ended before it: an error in an earlier request or script, a group that did not run), null when nothing is known; `stats` (`raceStats()`): `spreadMs` (first to last send), `offBy` (`{ min, max }` of sent − planned over on-time VUs), `peakInFlight` + `peakAt` (sweep over [sent, sent + ms], a send before an end at the same instant, so two that share a millisecond overlap), `newConnections`, `marginMs` (smallest planned − arrived: the lead time the slowest VU had left; negative = late). Checked with real k6 (`test/race-k6.test.js`): each record's send time is 0–1 ms after the pre-processor's `Date.now()`, 200 VUs "together" report 0 new connections (the server's socket count agrees) and the 50-VU control without warm-up reports 50 of 50. The Overview's "Race burst" card (both modes): a note (all in time / N late, raise the lead time / only N of M sent), figures (T0 as a clock time, VUs that sent, first to last send, sent vs planned, peak in flight, new connections, tightest margin), a Gantt (`raceGantt()`: one row per VU by planned time, first 100; bar from send to response, tick at the planned time, dashed line at the peak; colour = the outcome label in rule order on `--tone-1` … `--tone-8`, the fallback and labels past the eighth on `--tone-other`, one colour and no legend without outcome rules; a `<title>` per row with every value) and a table with every VU (first 500). Late and missing VUs are entries under Errors (`raceErrors()`). The report has the same section (the Gantt as inline SVG, light and dark tones, every VU up to 2,000).
- Live metrics (`server/live-metrics.js`, `server/k6-runner.js`): before spawning, the runner asks the OS for a free port on 127.0.0.1 and starts k6 with `--address 127.0.0.1:<port>` (k6 exits with code 106 when its REST API port is taken; two runs at once no longer both ask for k6's default `localhost:6565`), then polls `GET /v1/metrics` there every second (the first poll one second in; each answer within the second, `node:http`, no keep-alive) until k6 exits or the run is stopped; an answer still on its way is dropped, so no `metrics` event follows `done`. A poll that fails (k6 still starting, refused, an error status, not JSON, no answer in time) is skipped and never reaches the run; without a free port k6 starts as before and no `metrics` events are sent. The REST API is read from outside k6: the generated script is unchanged and no sample costs anything. Outcome counts come from the same submetrics as `done` (each label's `count>=0` threshold makes k6 report it there too). `/api/run` adds `outcomes` (`readOutcomeResults()` over the live counts) and `outcomeThresholds` (`readLiveOutcomeThresholdResults()` in `public/js/outcome-thresholds.js`): a count only grows, so `<` / `<=` broken and `==` passed are already `not-met`, `>` / `>=` reached is already `met`; otherwise `on-track` (holds so far, may still break) or `not-yet` (may still be met); `unknown` while the label has no count. k6's own answer in `done` is final. The Overview's Outcomes (`public/js/outcome-results.js`) shows them live with a note, updating the same rows in place (bar widths glide), and `done` replaces them; a stopped or interrupted run keeps the last live values, marked as the counts when it was stopped. Live requests, response times and VUs are in the event but not shown yet (a later live chart reads them). k6's p95 there is cumulative, never per second.
- Assertion type list: `ASSERT_TYPES` in `public/js/components/request-editor/checks.js` — **must stay in sync** with the switch in `server/generator/assertions.js` and the recognized shapes in `server/importer/checks.js`.
- Script import (`importK6Script`) is a best-effort reverse of the generator: it reads straight-line request flows, never runs the script, and reports everything it skips as warnings. Imported requests start with `checkStatus: false` unless the script has K6UI's own 2xx/3xx check (or, for a request with expected statuses, a check of exactly that list). Scripts written by K6UI import back to the same flow (covered by `test/script-import.test.js`), except pre/post scripts and gRPC, which come back as plain requests or warnings. When the generator gains a new construct, teach the importer the same shape (e.g. a single `per-vu-iterations` scenario in `options.scenarios` imports as iterations mode; other scenarios are skipped with a warning). A `SharedArray` / `k6/data` import is not rebuilt into a data file: it is a warning, except that K6UI's own `DATA_n_ROW.column` references come back as `{{column}}`. An `if` is skipped with a warning that its requests were left out, except the exact shape the generator writes for a "Run only if" group (no `else`, not inside `group()`), which comes back as a group with that `runIf`.
- JMeter import (`importJmx`) reads the first enabled thread group (setUp/tearDown and further thread groups become warnings) and follows JMeter scope: config elements, timers, assertions and extractors apply to every request at their level and below. Header Managers at test plan / thread group level → `globalHeaders`; a controller directly under the thread group → request group (deeper controllers are merged into it); other Header Managers → request headers. Requests keep JMeter's failure rule via `checkStatus: true` unless a Response Assertion has "Ignore status". Timers pause *before* a request, so the pause is added to the previous request's `sleepAfter` (the first request's wraps to the last). Variable names are renamed to valid, non-reserved identifiers everywhere they appear. A thread group with a fixed loop count and no scheduler duration ("N loops per user") becomes `{ mode: "iterations", vus: <threads>, iterations: <loops> }`; its ramp-up is not supported there (all VUs start at once, with a warning when more than one user ramps up). Forever loops, scheduler durations and Concurrency Thread Groups keep the duration/stages profile. A `CSVDataSet` becomes a data file (`jmx/data.js`): `variableNames` → `columns` (renamed like other variables), `ignoreFirstLine` → `skipHeader`, `delimiter` (`\t` = tab), `shareMode.all` → `next-row` and any other share mode → `per-vu` (with a warning), `recycle` → `recycle` and otherwise `stop`; `${FILE_VAR}` file names resolve through User Defined Variables. A .jmx has no rows, so it is imported with empty `content` and a warning to upload the file; another warning names a column that is also extracted by a request (not for a data set of a turned-off group). A data set inside a controller gets the `groupId` of the group it sits in, so its row is read, and `stop` applies, only when that group runs; one in a controller nested deeper than the group warns (it is read when the group starts), and one below a disabled nested controller is skipped with a warning. A group is kept while a request or a data set refers to it. An **`IfController`** directly under the thread group becomes a group with `runIf` when its condition is a known shape (`condition.js`; the text is tokenized, never evaluated): with "Interpret Condition as Variable Expression" on, `${__groovy(...)}` / `${__jexl3(...)}` / `${__javaScript(...)}` around the body; with it off, the JavaScript expression itself. Bodies read: `def m = props.get('X') ?: vars.get('X'); return m == 'A' || m == 'B'` (groovy only, `props` or `vars`, also bare `vars.get('X') == 'A'`), and `${X} == "A"`, `"${X}" == "A"`, `'${X}' == 'A'`, with `!=` (a single comparison → `not-equals`) and `||` over the same variable (→ `equals` / `one-of`); parentheses are allowed. Anything else (an empty value, a value with a comma or surrounding spaces, `&&`, different variables, mixed `==` / `!=`, method calls) is not read: the group keeps running every iteration and the warning quotes the condition. The variable name goes through the usual renaming; one that the plan never defines becomes an empty global variable with a warning, and a condition that also reads a JMeter property (`props.get`) says that K6UI only reads the variable. "Evaluate for all children" warns (K6UI checks once, when the group starts). A disabled `IfController` stays a disabled group with its condition. An `IfController` nested deeper is merged into its group and its condition is ignored, with a warning. The "logic is not supported" warning remains only for logic controllers that are not read.

## Conventions

- UI text, code comments, and error messages: English.
- Kebab-case file names; the frontend stays vanilla JS (do not add a framework/bundler unless asked).
- Simple and Advanced are two layouts over one DOM: never clone, move, or re-render request cards per mode, and never store the mode in project data (rules in `docs/ui-modes.md`).
- Render project data (names, URLs, labels) with `textContent`, never `innerHTML`.
- Styling uses the tokens in `css/tokens.css` (no raw colours or one-off sizes in the other files). Text must keep WCAG AA contrast on its surface; the browser check measures it.
- Help: a term a newcomer may not know gets a `?` button (`data-help="<key>"`, key in `public/js/glossary.js`) next to its label or heading, never inside a `<label>` (a radio card is the one exception: its radio is named with `aria-labelledby`); `test/help-glossary.test.js` checks every key has an entry.
- Icons: put `data-icon="name"` on the element (names in `css/base.css`); a new icon is one `--i-name` mask in `tokens.css` plus one line in `base.css`. No icon fonts, images, or network assets.
- Adding a view: a nav entry in `index.html` (under the fitting sidebar section, and a step mapping in `nav.js` for Simple), a `<section id="view-name" class="view hidden">`, a title in `nav.js`, and a section in `css/views.css`. A category that belongs on an existing Simple page is a `.view-block[data-block="<category>"]` of that page plus a `PAGE_OF` entry in `nav.js`, not a new view.
