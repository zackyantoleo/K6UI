    New to load testing? It takes three steps

    1. 1 · Build Flow Write down what a user does For example: log in, open the profile, create an order. One request per step.
    2. 2 · Load & goals Choose how much traffic Start with a smoke test: 1 user for 30 seconds, to prove the flow works.
    3. 3 · Run & Results Read the verdict Passed or failed against your goals, with the slowest request and the errors.

    Start from

    Values your requests reuse. Change one here and every request that uses it follows. Everything on this page is optional.

    Variables

    Use one as {{name}} in a URL, header, or body. Tip: put the server address in {{base_url}}, so moving to another environment is one change. Names use letters, digits, and underscores, and do not start with a digit.

    Shared headers

    Sent with every request, such as Accept or Authorization: Bearer {{token}}. A request's own header with the same name wins (names are not case-sensitive).

    CSV data files

    The rows are saved inside the project file and written into the generated script. If a file holds passwords or tokens, treat both of them as secrets.

    Drag a .csv file here

    Each iteration reads one row, so users do not all log in as the same person. A column becomes {{column_name}}. Up to 5 MB per file, 10 MB in total.

    A value taken from a response with the same name as a column replaces the file's value for the requests after it.

    Steps
    All VUs start together.
    Each VU runs the whole flow this many times, then stops.
    Safety limit: k6 stops the test if it is still running after this long.
    The requests before it (logging in, for example) run first for every user. Then every user sends this one at its planned time.
    Each VU runs the flow once. A number, or a global variable like {{RACERS}}.
    Separated by commas: VU 1 sends at T0 + the first offset, and so on. A global variable like {{T2_MS}} works too.

    Advanced timing

    T0 = when setup ends + this. It must cover starting the VUs and the requests before the race request; a VU that gets there later is reported as late.
    Each VU sends a GET to the warm-up path on the race request's host before it waits, so the race request reuses an open connection. Any status is fine, and it still counts in the request total and the response times.
    Off: a late VU is a warning in Run & Results.
    Safety limit: k6 stops the test if it is still running after this long.

    Pass or fail

    The test is marked Failed when a goal you switched on is missed (k6 exits with code 99, so a CI pipeline can stop a release). 500 ms and 1% are common starting points for an API; ask your team for the real numbers.
